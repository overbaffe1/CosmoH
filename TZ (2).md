## 1. Суть продукта

**Основная задача системы — управление потоком заданий.** Не рисование расписаний и не визуализация телеметрии. Сервис принимает поток коммерческих заданий, оценивает каждое по деньгам и срочности, считает его ресурсную себестоимость **до запуска**, решает какие задания вообще брать в работу и в каком порядке, и раздаёт их аппаратам. Оператор наблюдает и вмешивается только событиями.

Конвейер обработки задания:

```
ПОСТУПЛЕНИЕ  →  ОЦЕНКА          →  СЕБЕСТОИМОСТЬ  →  ДОПУСК       →  ДИСПЕТЧЕРИЗАЦИЯ →  ИСПОЛНЕНИЕ →  УЧЁТ
(план+события)  (деньги+срочность)  (энергия/слоты/   (брать или нет)  (кому и когда)     (борт)        (выручка/
                                     шаги/тепло)                                                         потери)
```

Каждый этап конвейера — отдельный модуль с отдельными тестами. Это ядро репозитория.

### 2.1 Связь — аппараты доступны по очереди

| Показатель | P02 / P03 / P04 (48 КА, 288 шагов) |
|---|---|
| Окно downlink-контакта на аппарат | **7–12 шагов из 288** (медиана 9) — около 3% смены |
| Одновременно в downlink-контакте | **0–3 аппарата** (медиана 2) |
| Доступность relay на аппарат | **286 из 288 шагов** |
| Глобальный лимит downlink | 2 аппарата на шаг |

**Вывод для архитектуры:** Земля видит аппарат считанные минуты за смену. Всё остальное время он обязан работать по загруженному заранее заданию. Relay при этом доступен почти всегда — это и есть работа, которую аппарат делает автономно.

### 2.1.1 Связь с Землёй держится на одном аппарате — жёсткое ограничение

Требование кейсодержателя (А. Паршин): **связь с Землёй должна поддерживаться постоянно, хотя бы один аппарат обязан быть подключён**. Если распределить все функции «без связи» — только калибровка и задания — связь пропадёт.

Данные показывают, насколько это узкое место:

| Ситуация | P02 / P03 / P04 | P01_intro |
|---|---|---|
| Шагов, где связь держит **ровно один** аппарат | **133 из 288 (46%)** | 7 из 48 (15%) |
| Шагов с 2 аппаратами в контакте | 134 | — |
| Шагов с 3 аппаратами | 19 | — |
| **Шагов полной слепоты** (нет ни downlink, ни relay ни у кого) | **2** — шаги 224 и 230 | **41 из 48 (85%)**, максимум 37 подряд |

Отсюда два следствия:

1. **Почти в половине смены существует ровно один аппарат-шлюз.** Поставить его на калибровку = потерять связь с Землёй. Планировщик обязан распознавать такие шаги и защищать шлюз. Это ограничение **отсутствует в модели** и реализуется нами как политика диспетчеризации (см. 3.4, правило 5).
2. **Требование «постоянно» буквально невыполнимо**: на шагах 224 и 230 связи нет ни у одного аппарата — оба канала пропадают одновременно. Правило формулируется как «поддерживать связь всегда, когда это физически возможно», а эти два шага фиксируются как задокументированный разрыв, а не как ошибка алгоритма.

**`P01_intro` — готовый демо-кейс автономии:** 85% смены группировка вообще не видит Землю, максимальный разрыв 37 шагов (более 3 часов). Именно на нём показывается работа бортового агента по загруженному бандлу.

### 2.2 Дефицит ресурсов — структурный и доказуемый до запуска

| Сценарий | Downlink | Relay: спрос vs ёмкость | Энергодефицит | Деньги на столе |
|---|---|---|---|---|
| `P02_shift` | 410 слотов из 576; **у 9 из 48 КА спрос больше собственного окна связи** | 1 707 из 13 824 | 0 из 48 КА | $28 773 (P3: $7 051) |
| `P03_energy` | то же | то же | **24 из 48 КА** (генерация 767 Вт·ч против 1 917 в норме при базовом потреблении 432 Вт·ч) | $28 773 |
| `P04_demand` | то же | **15 389 из 13 824 — переподписка 111%** | **34 из 48 КА** | $208 884 (P3: $43 019) |

**Это и есть обоснование продукта.** В `P04_demand` выполнить всё физически невозможно: ёмкость группировки меньше спроса ещё до учёта энергии и калибровки. Значит единственный осмысленный вопрос — **какие задания брать, чтобы собрать максимум денег и обязательств**. Именно это система и решает.

Те 9 аппаратов, у которых downlink-спрос превышает собственное окно связи, дают **проверяемое обоснование невыполнимости** — прямое требование критерия О3, закрытое арифметикой, а не отговоркой «алгоритм не нашёл».

### 2.3 Жёсткие правила модели

Прочитано из `model/resource_env.py`, менять нельзя:

| Правило | Значение |
|---|---|
| Шаг / горизонт / КА | 300 с ровно / 1…288 / 1…48 |
| Действие на шаге | одно на аппарат: `idle` \| `calibrate` \| `job` |
| Downlink на шаге | не более 2 по всей группировке |
| Одно задание на шаге | один исполнитель |
| Энергорезерв 30% SOC | проверяется **дважды** — и до, и после шага |
| Температура −5…+45 °C | проверяется **дважды** |
| Калибровка | годна 48 шагов (4 ч), обновляется за 1 шаг, при `age >= 48` любое задание отклоняется |
| Окно задания | `release <= k < deadline`; завершение ровно на `deadline` **засчитывается** |
| Выручка | только за полностью завершённое в срок, один раз, по `value_usd` |
| Частичная работа | приносит **ноль**, но ресурсы уже потрачены |

Последняя строка — экономический стержень задачи. Начатое и незавершённое задание это чистый убыток.

## 3. Экономическое ядро (главный модуль, Dev A)

### 3.1 Ресурсная себестоимость задания — считается ДО выполнения

Для пары «аппарат `s` — задание `j`» рассчитывается **карта стоимости**, доступная оператору до запуска:

```python
@dataclass(frozen=True)
class CostCard:
    energy_wh: float              # ватт-часы на весь объём работы
    energy_pct_of_usable: float   # доля пригодного запаса батареи
    ground_slots: int             # слоты наземного сегмента (для downlink)
    sat_steps: int                # шаги аппарата — самый дефицитный ресурс в P04
    thermal_rise_c: float         # сдвиг равновесной температуры
    calibration_share: float      # доля израсходованного ресурса калибровки
    feasible: bool
    blocking: str | None          # конкретная причина невыполнимости
```

Формулы (числа — для типового аппарата: 140 Вт·ч, base 18 Вт, downlink 90 Вт, relay 65 Вт):

| Величина | Формула | Downlink | Relay | Калибровка |
|---|---|---|---|---|
| Энергия за шаг | `payload_w * 300/3600 / 0.95` | **7.89 Вт·ч** | **5.70 Вт·ч** | 1.75 Вт·ч |
| Сдвиг равновесной T | `0.2 * (base_w + payload_w)` | **+21.6 °C** | **+16.6 °C** | +7.6 °C |
| Пригодный запас батареи | `capacity * (SOC − 30%)` | при SOC 68% — **53.6 Вт·ч** | | |
| Шагов работы от батареи | | **≈ 6.8** | **≈ 9.4** | |

Тепловой сдвиг не декорация: `+21.6 °C` при интенсивном downlink на аппарате, уже разогретом внешними условиями, упирается в `payload_max_c = 45 °C` и блокирует работу. Это входит в себестоимость.

### 3.2 Оценка задания: деньги × срочность

**Удельная доходность** — деньги на единицу дефицитного ресурса:
```
yield(j) = value_usd / work_steps        [$ за шаг аппарата]
```

**Срочность** — через дефицит возможностей, а не через календарь:
```
opportunities(j,k) = |{ k' in [k, deadline) : существует s из eligible(j),
                        s доступен и env[s][kind + '_available'][k'] }|

tightness(j,k) = remaining_steps / max(1, opportunities(j,k))
```

| `tightness` | Смысл | Действие системы |
|---|---|---|
| `> 1` | **Доказуемо невыполнимо** — окон меньше, чем требуется работы | Отклонить с перечислением недостающих окон |
| `= 1` | Критично — каждое оставшееся окно обязано быть использовано | Жёсткое закрепление, ресурс резервируется |
| `< 1` | Есть запас | Можно отложить; срочность растёт как `tightness^γ`, γ ≈ 2 |

Именно это даёт **проверяемое основание** для утверждения о невыполнимости.

### 3.3 Теневые цены ресурсов — механизм принятия решения

Ключевая идея: ресурсы дефицитны по-разному в разные моменты смены, поэтому у каждого ресурса есть **текущая цена в долларах**, и задание запускается только если приносит больше, чем расходует.

| Цена | Что означает | Как оценивается |
|---|---|---|
| `λ_G` | стоимость слота наземного сегмента, $/слот | удельная доходность маргинального downlink-задания, ещё влезающего в оставшуюся ёмкость (дуал задачи о рюкзаке) |
| `λ_E(s)` | стоимость ватт-часа на аппарате `s`, $/Вт·ч | около нуля, пока энергия не связывает; растёт при прогнозе ухода под резерв в горизонте `lookahead` |
| `λ_W(s)` | стоимость шага аппарата `s`, $/шаг | доходность вытесняемого кандидата; главный дефицит в `P04_demand` |

**Чистая ценность запуска:**
```
NV(s,j,k) = value_usd * U(tightness) * Π(priority)
            − λ_G * ground_slots
            − λ_E(s) * energy_wh
            − λ_W(s) * remaining_steps
```

`Π(priority)` — множитель режима: в «приоритетном обслуживании» доминирующий для P3 (выручка остаётся тайбрейком), в «коммерческой отдаче» равен 1.

Назначение на шаге — максимизация суммы `NV` при ограничениях: жадность по `NV` с резервированием downlink-слотов, при запасе времени — венгерский алгоритм на двудольном графе «аппараты × задания».

### 3.4 Допуск в работу (admission control) — регулирование потока

Прямое следствие правила «частичная работа приносит ноль»:

1. **Не начинать то, что не успеть.** Если прогноз не даёт завершения в срок — задание не запускается вообще. Метрика `work_steps_in_missed_jobs` (есть в модели) — прямой показатель качества этого решения, её надо минимизировать.
2. **Не начинать то, что убыточно.** `NV <= 0` → задание уходит в очередь ожидания, а не в работу.
3. **Вытеснение и перераспределение.** Поступившее срочное задание с высоким `NV` может вытеснить начатое с низким — но только если потерянная работа меньше выигрыша. Прерванное relay-задание может быть подхвачено другим допустимым исполнителем с сохранением прогресса; downlink-задание закреплено за своим аппаратом и перераспределению не подлежит. Это прямое требование кейсодержателя: «возможно, прервать выполнение задания, возможно, перераспределить между членами группировки».
4. **Каждое отклонение с причиной** из фиксированного списка: `infeasible_by_contacts`, `infeasible_by_energy`, `infeasible_by_deadline`, `negative_value`, `preempted_by`, `ground_capacity_reserved`, `gateway_protected`. Причины не смешиваются.
5. **Защита шлюза.** На каждом шаге вычисляется множество аппаратов с `downlink_available = true`. Если оно непусто, минимум один из них резервируется как канал связи с Землёй: ему запрещается калибровка, он получает либо downlink-задание, либо удержание связи. Приоритет резервирования — аппарату с наименьшим числом оставшихся окон контакта. Если множество пусто (шаги 224, 230) — фиксируется разрыв связи с явной отметкой в журнале.

### 3.5 Предполётная оценка смены

Отдельный экран и отдельный API-метод — **до первого шага расчёта**:

- суммарный спрос по каждому ресурсу против ёмкости (слоты, шаги, Вт·ч);
- коэффициент переподписки по каждому ресурсу;
- список структурно невыполнимых заданий с причиной;
- потолок достижимой выручки по релаксации — сколько денег на столе вообще;
- прогноз узких мест по шагам смены.

На `P04_demand` экран сразу показывает переподписку 111%, то есть объясняет, почему часть заданий будет отброшена, **до** запуска расчёта.

## 4. Архитектура автономии

### 4.1 Статус этой части

Модель кейса **не моделирует командный канал**: `env.step(actions)` принимает команды для всех аппаратов на каждом шаге независимо от связи. Ограничения `downlink_available` / `relay_available` действуют на *выполнение заданий*, не на *доставку команд*. Ограничения «хотя бы один аппарат на связи» в модели тоже нет.

Поэтому двухуровневая автономия и защита шлюза — **наше расширение модели**. Это не обходной путь, а явно одобренный организаторами способ получить баллы по О7 (см. 2.4), и одновременно прямой ответ на требование кейсодержателя о постоянной связи с Землёй.

Расширение строится **поверх** `model/`, а не вместо него: итоговые действия всё равно проходят через `env.step` со всеми проверками, учёт и `replay_episode` остаются эталонными. В README и на защите это называется своим именем — где кончается выданная модель и начинается наша надстройка.

### 4.2 Интерпретация каналов

| Сущность модели | Наша трактовка |
|---|---|
| `downlink_available[s][k]` | связь аппарата `s` с Землёй на шаге `k` — окно загрузки полётного задания |
| `relay_available[s][k]` | межспутниковая линия — канал раздачи заданий внутри группировки |
| аппарат с downlink-контактом | **шлюз**: принимает с Земли пакет для подгруппы и раздаёт его по межспутниковой линии |

Это прямо соответствует описанной картине: связь есть с одним аппаратом группы, он передаёт задания остальным.

### 4.3 Два уровня управления

**Уровень 1 — наземный планировщик (ЦУП).** Работает с полной картиной: все задания, все аппараты, теневые цены, предполётная оценка. Формирует **полётное задание (бандл)** для каждого аппарата:

```python
@dataclass
class Bundle:
    satellite_id: str
    issued_at_step: int
    valid_until_step: int
    queue: list[BundleItem]    # упорядоченный список заданий
    policy: OnboardPolicy      # правила поведения вне связи
    fallback: str              # что делать, когда очередь исчерпана

@dataclass
class BundleItem:
    job_id: str
    priority_rank: int         # порядок в очереди
    earliest_step: int
    latest_start_step: int     # позже начинать бессмысленно — не успеть
    min_soc_pct: float         # не начинать ниже этого SOC
    expected_cost: CostCard
    abandon_if: str            # условие отказа от задания
```

**Уровень 2 — бортовой агент.** На каждом шаге выбирает действие **локально**, зная только собственное состояние (SOC, температура, возраст калибровки, доступность канала) и свой бандл. Без обращения к Земле:

1. **Если аппарат помечен в бандле как шлюз на этом шаге — калибровка запрещена.** Он держит связь: выполняет downlink-задание либо остаётся в `idle` с причиной `gateway_hold`.
2. Если `calibration_age >= valid − margin` и в очереди есть работа → `calibrate`.
3. Иначе первый элемент очереди, проходящий локальные проверки (окно, `SOC >= min_soc_pct`, температура, канал доступен) → `job`.
4. Иначе правило `fallback`: восстановление заряда, профилактическая калибровка в простое или `idle` с зафиксированной причиной.

Роль шлюза закладывается в бандл заранее — наземный планировщик знает расписание окон контакта из входных данных и проставляет `gateway_steps` для каждого аппарата. Поэтому аппарат исполняет её и без связи с Землёй.

Бандл загружается только на шаге с контактом. Вне контакта аппарат живёт по последнему загруженному — **это и есть автономность**. При истёкшем `valid_until_step` агент переходит на консервативную политику.

### 4.4 Два режима управления — и измерение цены автономии

| Режим | Описание | Назначение |
|---|---|---|
| `centralized` | ЦУП решает за каждый аппарат на каждом шаге | верхняя граница качества, эталон сравнения |
| `federated` | бандлы + бортовая автономия, загрузка только в окна связи | реалистичный режим работы |

Разница метрик между режимами = **цена автономии в долларах**. Содержательный эксперимент, закрывающий сразу «сравнение вариантов» и «алгоритм планирования», и честный ответ на вопрос жюри «что даёт ваша автономия».

## 5. Роль оператора — надзор, не ручное управление

Система работает сама. Оператор:

1. **Настраивает смену**: сценарий, цель управления, при необходимости — начальный заряд аппарата, коэффициент солнечной мощности, приоритет задания.
2. **Смотрит предполётную оценку**: где дефицит, что невыполнимо, сколько денег на столе.
3. **Запускает и наблюдает**: поток заданий идёт автономно, видна лента решений и предупреждения.
4. **Вмешивается только событиями**: новое задание, недоступность аппаратов, отмена сеансов. Плюс смена цели на границе шага.
5. **Разбирает решения**: почему это задание взято, почему то отклонено, что помешало.
6. **Сравнивает варианты** и сохраняет результат.

Оператор **не** назначает исполнителей вручную и не редактирует внутреннее состояние — это прямо запрещено постановкой.

### Экраны

| Экран | Содержание | Приоритет |
|---|---|---|
| **Предполётная оценка** | спрос против ёмкости, переподписка, структурно невыполнимые задания, потолок выручки | высокий — главный дифференциатор |
| **Пульт смены** | KPI (выручка накопленная и прогнозная, P3 в срок, загрузка), лента решений, предупреждения о дефиците, управление ходом расчёта | высокий |
| **Поток заданий** | очередь: принято / в работе / ждёт / отклонено с причиной; карта стоимости каждого задания; фильтры | высокий |
| **Группировка** | карточки аппаратов: SOC, температура, калибровка, текущий бандл, окна связи на таймлайне | средний |
| **Разбор решения** | по клику на шаг: рассмотренные кандидаты, их `NV`, теневые цены в этот момент, блокирующее ограничение | высокий — критерий О3 |
| **Сравнение** | две ветви из одного состояния, дельты, вердикт | высокий |
| **Выгрузка** | машиночитаемый JSON + читаемый отчёт | средний |

## 6. Стек и структура

Ограничений по стеку нет. Рекомендация — **Python 3.11 + FastAPI** для ядра (прямое подключение `model/` снимает риск расхождения расчёта с эталоном, а это 10 баллов критерия Т1) и **React + TypeScript + Vite** для фронта. Деплой — один Docker-образ, статика раздаётся backend'ом.

```
/model/                       # выданная библиотека — НЕ ПРАВИТЬ
/backend/
  flow/                       # ЯДРО: управление потоком заданий
    valuation.py              # yield, tightness, urgency, Π(priority)
    cost.py                   # CostCard: энергия, слоты, шаги, тепло, калибровка
    shadow_prices.py          # λ_G, λ_E, λ_W
    admission.py              # допуск, вытеснение, очередь ожидания, причины
    dispatch.py               # назначение пар (аппарат, задание) на шаге
    preflight.py              # предполётная оценка смены
    explain.py                # разбор решений
  autonomy/
    bundle.py                 # формирование полётных заданий
    onboard_agent.py          # бортовая логика выбора действия
    uplink.py                 # окна связи, шлюзы, раздача бандлов
  planners/
    base.py                   # интерфейс Planner
    baseline.py               # простое правило: EDF / by-value / by-priority
    economic.py               # основной: теневые цены + admission
  analytics/
    metrics.py, diagnostics.py
  app/                        # FastAPI: api/, schemas/, core/
  tests/
/frontend/src/{pages,components,api,store,charts}
/experiments/
  preflight_analysis.py       # анализ из раздела 2 (уже написан)
  run_benchmarks.py
  results/
README.md, Dockerfile, docker-compose.yml
```

### Производительность

Требование: полный прогон `P04_demand` (288 шагов × 48 КА × 8 120 заданий) — **не дольше 20 с**.

Две обязательные меры:
- **Не вызывать `Environment.observation()` в цикле** — он делает `deepcopy` всех заданий. Планировщик ведёт собственное зеркало состояния.
- **Инкрементальные индексы**: `active_jobs` (обновляется на `release`, `deadline`, завершении), `jobs_by_sat[s]` (куча по дедлайну), `jobs_by_release[k]`. При `add_jobs` доиндексируются только новые.

### ЭТАП 5. Презентация и резерв (46–48 ч) — вместе

Ключевая линия защиты выстраивается вокруг цифр раздела 2:

> Спрос превышает возможности группировки на 11%, треть аппаратов в энергодефиците, связь с Землёй занимает 3% времени, и почти в половине смены её держит **единственный** аппарат. Поэтому задача не «составить расписание», а **выбрать, на чём заработать, не потеряв связь**. Наша система оценивает каждое задание в деньгах против стоимости ресурсов и принимает решение сама.

Три обязательных эпизода демо:
1. **Предполётная оценка P04_demand** — переподписка 111% видна до запуска.
2. **Защита шлюза на P02_shift** — показать шаг из тех 133, где связь держит один аппарат, и как система отказывает ему в калибровке.
3. **Автономия на P01_intro** — 37 шагов подряд без связи, аппараты работают по загруженному бандлу.

Демо прогоняется по секундам заранее. Отраслевые эксперты смотрят именно его, а не код (см. раздел 11), поэтому заминок быть не должно.

Заготовки ответов: почему такой метод, где он проигрывает, как доказывается невыполнимость, сколько стоит автономия, почему расширили модель, как обеспечена воспроизводимость.

## 11. Сдача решения и регламент проверки

Уточнено на сессии с организаторами (Д. Семенов).

### Двухэтапная проверка

| Этап | Кто | Что смотрит | Следствие для нас |
|---|---|---|---|
| 1. После stop-code | Технические члены жюри | Репозиторий: код, архитектура, воспроизводимость | **Технические 50 баллов решают допуск.** Отраслевые на этом этапе не учитываются |
| 2. Защита (топ-20…25 команд) | Отраслевые эксперты | Демонстрация сервиса, презентация, ответы на вопросы — **«независимо от того, что есть в коде»** | Отраслевые 50 баллов берутся живым демо, а не чтением кода |

Практический вывод для планирования работ: **сначала проходим техническую проверку, потом впечатляем на защите**. Поэтому в этапах 1–3 приоритет у корректности учёта, воспроизводимости и структуры репозитория, а полировка UI — после. Но к защите демо должно работать без единой заминки, потому что код там смотреть не будут.

### Куда сдавать

- Репозиторий размещается на **GitVerse** (не GitHub) — по инструкции организаторов в чате участников.
- Развёрнутый веб-сервис должен быть доступен жюри через браузер до окончания проверки.
- Комплект сдачи: ссылка на сервис и доступы, репозиторий с исходниками и инструкцией, описание метода и экспериментов (можно в README), примеры сохранённых расчётов, презентация.

### Формула оценки

Открытая: по каждому критерию оценки экспертов усредняются отдельно, затем средние суммируются. Максимум 100 (50 отраслевых + 50 технических). Единой автоматической метрики и эталонного расписания нет — значит выигрывает не «правильный ответ», а **обоснованность и демонстрируемость**.

### Что жюри может сделать на проверке

- загрузить собственный сценарий того же формата (до 48 КА, 288 шагов, сопоставимый объём заданий);
- изменить допустимые начальные условия;
- передавать новые сообщения **по одному** в процессе исполнения, не раскрывая будущие;
- сохранить выполненную историю перед подачей очередного сообщения.

Отсюда требование к устойчивости: сервис обязан корректно принять чужой JSON, внятно отвергнуть некорректный и ни при каких условиях не терять состояние. Формального рейтинга по времени отклика нет, но «пять минут модельного времени не требуют пяти минут ожидания».

## 12. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Экономическое ядро не успевает или хуже baseline | средняя | baseline готов на этапе 1 и остаётся переключаемым. Худший случай — сдаём baseline, честно объясняем |
| Производительность на P04 | высокая | индексы и зеркало состояния закладываются сразу, бенчмарк на этапе 1. Запас — ограничение перебора топ-N кандидатов |
| Автономный режим не успевает | средняя | `centralized` — основной режим, `federated` — доп. функция. Порядок реализации именно такой |
| Теневые цены нестабильны, решения «дёргаются» | средняя | сглаживание по скользящему окну, гистерезис на вытеснении; при неудаче — фиксированные веса |
| Память при `fork()` и хранении `explain` | средняя | `explain` только для запрошенных шагов, не более 3 активных ветвей |
| Расхождение расчёта с эталоном | низкая | никогда не переписывать `resource_env.py` под себя |
| Деплой в последний час | высокая | публичный URL поднимается **на этапе 1** |
| Рассинхрон контракта | средняя | заморозка на этапе 0, моки с первого часа, сверка каждые 4 часа |
| Жюри загружает свой сценарий, который падает | средняя | `validate` на любом входе, тесты на искусственно битых JSON |

## 13. Definition of Done

Посторонний человек с чистого ноутбука может:

1. Открыть публичный URL.
2. Загрузить `data/P04_demand.json` и **увидеть до запуска**: спрос превышает ёмкость на 11%, 34 аппарата в энергодефиците, вот эти задания невыполнимы и почему, потолок выручки такой-то.
3. Открыть любое задание и увидеть его карту стоимости: сколько ватт-часов, слотов, шагов и градусов оно стоит на каждом допустимом исполнителе.
4. Изменить начальный заряд аппарата и приоритет задания, сохранить как новый сценарий.
5. Выбрать цель и режим, запустить — и наблюдать, как система **сама** решает, что брать в работу.
6. Подать `examples/events_demo.json`, увидеть перестроение потока и что удалось сохранить.
7. Кликнуть любое решение и получить разбор: кандидаты, их чистая ценность, теневые цены в этот момент, блокирующее ограничение.
8. Вернуться к контрольному шагу, создать две ветви, сравнить и прочитать вердикт.
9. Увидеть, сколько стоит автономия — разницу между централизованным и федеративным режимом в долларах.
10. Открыть `P01_intro` и увидеть, как группировка работает 37 шагов подряд без связи с Землёй.
11. Убедиться, что на шагах с единственным аппаратом в контакте система не отправила его на калибровку.
12. Скачать машиночитаемую выгрузку и читаемый отчёт.
13. Загрузить выгрузку обратно и получить подтверждение воспроизведения.
14. По README развернуть то же локально за 10 минут и получить те же числа.
