# Плейбук КосмоХакатона 18–20.09.2026: два окружных онлайн, два решения

Рабочий документ для участия онлайн одновременно в **Красноярске (СФО)** и **Санкт-Петербурге (СЗФО/ЦФО)**.
Составлен 18.09.2026 на основе Положения (`regulation.pdf`) и чатов (см. `brief.md`).

**Как это использовать по правилам.** Пп. 9.5/9.6 и 11.1: можно применять свои ранее созданные
компоненты, но нужно раскрыть источники и показать вклад в окне хакатона. Схема:

1. Создать **два репозитория сдачи** (по одному на город), история коммитов — с 18.09 18:30.
2. Первым коммитом положить каркас и в README раздел **Disclosure**: что взято из заготовки,
   что сделано в окне хакатона, какие открытые библиотеки/данные использованы.
3. Содержательную работу (данные, модель, интерфейс, метрики, текст презентации) делать в окне
   хакатона и коммитить с понятными сообщениями — это доказательство вклада.

## 0.5 Критично до старта: собрать команду 3–5 человек

Положение (п. 5.2–5.3): команда — **3–5 человек**, один участник — только в одной команде в рамках
хакатона. Сейчас участник один → нужно **минимум +2 человека в каждом городе** (Красноярск и СПб —
разные хакатоны, значит и команды разные).

Готовые тексты объявлений для чатов, список нужных ролей, план «если никого не нашли» и
быстрый онбординг — в отдельном файле: [`team-recruiting.md`](team-recruiting.md).

## 1. Схема двух городов

| | Красноярск | Санкт-Петербург |
|---|---|---|
| Кейс | «Оперативный мониторинг лесных пожаров» | «Орбитальный риск» |
| Наш репозиторий сдачи | `cosmohack-krasnoyarsk-fires` | `cosmohack-spb-orbital-risk` |
| Заготовка | `starter/fires-krasnoyarsk` | `starter/orbital-risk-spb` |
| Ядро защиты | метрика + рабочий сервис с картой | риск-индекс ВКД + окна безопасности |
| Критичное время | стоп-код 19.09 (уточнить МСК/местное!) | стоп-код 19.09 23:30 МСК, защита 20.09 10:30–17:30 |
| Сильная сторона для жюри | объективные метрики + га в гектарах | редкая тема + дозовые лимиты + окна ВКД |

**Синергия:** одна архитектура (`данные → расчёт → индекс/метрика → FastAPI → дашборд`),
разный код и предметка. Один человек держит инфраструктуру (репозитории, деплой, презентации).

## 2. Роли (для команды 3–5 человек)

**Контекст: сейчас участник один.** До старта разработки задача № 1 — добрать +2 человека в каждый
город (см. `team-recruiting.md`). Пока команда не собрана, работаем по «соло-минимуму»: только то,
что уже есть, плюс живые данные; тяжёлые новые модули не пишем.

Если команда 3 человека (минимум по Положению):

| Роль | Зона | Что делает |
|---|---|---|
| A. Данные/ML | оба города | FIRMS/Sentinel-2 (КРС), SWPC (СПб): провайдеры, кэш, признаки |
| B. Backend/деплой | оба города | FastAPI, докер, публикация демо, стабильность API |
| C. Фронт/дизайн + презентации | оба города | веб-карта, дашборд, слайды, питч, видео |

Если 4–5 человек: добавить «аналитик/предметник» (ДЗЗ/радиация — знать физику на защите) и
«питч-мейкер» (текст выступления, ответы жюри, тайм-менеджмент чек-поинтов).

## 4. Сценарий защиты (5 минут на решение)

Опора: критерии кейсов + п. 14.3 (при равенстве выше «практическая применимость», затем
«готовность/реализуемость»). Значит структура: проблема → решение → **живое доказательство** →
применимость → ограничения.

| Мин | Блок | Ключевая фраза |
|---|---|---|
| 0:00–0:40 | Проблема и её цена | «Диспетчер получает сотни точек и тратит часы на отсев ложных. Мы отдаём 5–10 ранжированных очагов» |
| 0:40–1:40 | Что сделано | «Пайплайн: детекции → отсев ложных → очаги → площадь гари. Всё на открытых данных, работает оффлайн» |
| 1:40–2:40 | **Демо на экране** | живая карта, клик по очагу, метрика на экране. Не говорить «потом покажу» |
| 2:40–3:30 | Метрики и честность | «F1 0.94 по точкам, 1.00 по очагам, ошибка площади 0.6 %. На реальных снимках ожидаем IoU 0.80–0.93: облачность и тени» |
| 3:30–4:20 | Применимость | «REST + GeoJSON — встраивается в существующие ГИС; стоимость — один контейнер, данные бесплатны» |
| 4:20–5:00 | Ограничения и развитие | «Знаем слабое место: потери у промзон, настраивается порогом; дальше — обучение на подтверждениях Авиалесоохраны» |

Для СПб акценты другие: **редкая тема**, дозовые лимиты (1 мЗв на ВКД), окна безопасности,
заблаговременность 31 ч, «правило доминирующей опасности» (почему средневзвешенный индекс опасен).

### Заготовки ответов на вопросы жюри

**Пожары**
* «Почему не готовая модель?» — Решение интерпретируемое и объяснимое: по каждому решению видно вклад
  признаков (`/api/analyze` → `explanation`). Готовую модель нельзя проверить и сложнее защищать;
  мы оставили точку расширения — обучение на подтверждениях Авиалесоохраны.
* «Откуда метрика, если разметки нет?» — На демо-сцене эталон генерируется вместе с данными
  (известно, где очаги), на живых данных метрика считается по подтверждениям из сводок и по
  согласованности нескольких спутников (несколько аппаратов видят один очаг).
* «Что с ложными у промзон?» — Осознанный компромисс: штраф за близость к известным источникам.
  Видно на карте: очаг у Саяногорска отброшен. Порог настраивается — это риск-менеджмент, а не баг.
* «Как быстро обновляется?» — Модуль инкрементальный: при часовом обновлении обрабатываются только
  новые детекции; сцена из 77 детекций считается меньше секунды.
* «Площадь гари в гектарах — как проверяли?» — dNBR и пороги USGS, плюс морфологическая чистка;
  на синтетике IoU 0.994, на реальных снимках ожидаем ниже — это указано в README как ограничение.

**Орбитальный риск**
* «Почему максимум, а не среднее?» — Оперативные правила ВКД консервативны: один «красный» фактор
  отменяет выход. Среднее маскирует SPE при спокойном Kp — это ложное «можно», самый опасный класс ошибки.
* «Откуда лимит 1 мЗв?» — Упрощённо по NASA STD-3001 (порядок величины лимита на ВКД); в README
  указано, что модель инженерная и в продакшене заменяется расчётом по спектру (AP-8/AE-8, SPENVIS).
* «Учитываете ли орбиту?» — В дорожной карте: связка окон с витками по TLE и временем выхода;
  сейчас риск считается по времени, доза — с раздельными вкладами протонов и захваченных частиц.
* «Чем отличается от графиков NOAA?» — Мы даём решение, а не данные: индекс, класс, дозу за выход,
  окна и рекомендацию «можно/нельзя» + причину. Плюс API для ЦУП.
* «Прогноз есть?» — Сейчас nowcast + окна; прогноз (persistence + авторегрессия по Dst/Kp) в плане,
  и это не влияет на текущую рекомендацию.

## 5. Чек-лист сдачи (п. 9.3 Положения)

- [ ] Репозиторий сдачи: публичный, README с запуском, архитектурой, данными, лицензиями.
- [ ] Прототип/демо: локальный запуск одной командой + (по возможности) публичный деплой.
- [ ] Презентация: PDF (+ HTML) — `docs/presentations/`.
- [ ] Видео: если требует кейс — 2–3 минуты, запись демо с голосом.
- [ ] Раздел «Ценность» и «Ограничения» — есть в README и на предпоследнем слайде.
- [ ] Disclosure: что сделано в окне хакатона, какие открытые библиотеки и данные использованы.
- [ ] Проверка «с нуля»: клонировать в чистую папку, поставить зависимости, запустить тесты и демо.
- [ ] Стоп-код: последний коммит до дедлайна; после — не трогать репозиторий (п. 8.5).
