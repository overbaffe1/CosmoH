# КосмоФАЙР-2 — решение кейса «Двухэтапный мониторинг природных пожаров по данным ДЗЗ»

КосмоХакатон · Красноярск · 18–20 сентября 2026.

Решение состоит из трёх сдаваемых частей, ровно как требует постановка:

| Часть | Что это | Где смотреть |
|---|---|---|
| **AF-модуль** | детекция активного горения по чипу VIIRS 375 м (I1–I5 + вспомогательные слои), бинарная маска | `fires/af.py`, `fires/blobfilter.py` |
| **BS-модуль** | картирование гари и степени поражения 0–3 по паре Sentinel-2 до/после и Sentinel-1 | `fires/bs.py` |
| **`submission.csv`** | RLE-маски по шаблону `sample_submission.csv` | `inference.py`, `fires/submission.py` |
| **Сервис** | информационно-аналитический сервис: REST API, GeoJSON/Shapefile, справка по площадям | `service/` |

Плюс сопутствующие артефакты: подбор параметров (`train.py`), метрика соревнования с абляциями (`evaluate.py`),
отчёт (`docs/report.md`), презентация (`docs/presentation.pdf|html`), тесты (`tests/`, 40 тестов).

**Нужен только финальный ответ для организаторов?** Минимальный путь — три команды; полный порядок
действий с таймингами и проверками лежит в [`RUNBOOK.md`](RUNBOOK.md):

```bash
pip install -r requirements.txt
python -m fires.chips --data-dir ./test_data                              # диагностика раскладки
python inference.py --data-dir ./test_data --output submission.csv --validate
```

## 1. Быстрый старт

```bash
pip install -r requirements.txt

# 1) обязательная команда из постановки (без интерактива, exit code 0)
python inference.py --data-dir /path/to/test --output submission.csv --validate

# 2) подбор параметров на обучающей части (переобучение под реальные данные)
python train.py --data-dir /path/to/train --out weights/weights.json

# 3) метрика соревнования и абляции (для отчёта)
python evaluate.py --data-dir /path/to/train --ablation

# 4) сервис: каталог сцен + REST API + веб-карта
python -m service.catalog --data-dir /path/to/train --out service/catalog.json \
       --max-bs 30 --min-contour-ha 1.0
uvicorn service.app:app --host 0.0.0.0 --port 8000

# 5) тесты
pytest tests -q
```

Данные организаторов, если их нет локально, забираются скриптом (те же архивы лежат в репозитории команды):

```bash
bash tools/fetch_data.sh               # → /tmp/firesdata/real/train, AF 420 + BS 224
```

Подробный runbook (что где запустить, сколько это занимает, что проверить перед загрузкой сабмита) —
[`RUNBOOK.md`](RUNBOOK.md).

Если реального набора под рукой нет — работает синтетический стенд (smoke-тест конвейера; итоговые числа
получены на реальных данных, см. раздел 3):

```bash
python -m fires.synthetic /tmp/firesdata/dev2 --n-af 60 --n-bs 30 --seed 11 --clean
python evaluate.py  --data-dir /tmp/firesdata/dev2 --weights weights/weights.json --ablation
python inference.py --data-dir /tmp/firesdata/dev2 --output /tmp/submission.csv --validate
```


**Первое, что нужно сделать на реальных данных** — диагностика раскладки: организаторы не публикуют имена файлов,
поэтому `fires/chips.py` распознаёт каналы по шаблонам, а команда печатает, что именно найдено:

```bash
python -m fires.chips --data-dir /path/to/train
```

## 2. Что именно делает решение

### 2.1. AF: детекция активного горения

1. **Скрининг.** Исключаются вода (WorldCover 80), невалидные пиксели и пиксели без термального наблюдения
   (NaN в I4/I5). Солнечный блик не выбрасывается (внутри блика может быть настоящий очаг), а переводится в
   «подозрительный» режим: нужен ΔT выше порога не менее чем на 9 K либо I4 ≥ 335 K.
2. **Раздельные дневные и ночные шкалы.** Днём фон I4 прогревается до 310–315 K, ночью — до 283 K, поэтому пороги
   зависят от зенитного угла Солнца (95°): насыщение 367/340 K, «очень яркий» очаг 360/310 K, минимум кандидата
   330/295 K, ΔT = I4 − I5 25/10 K. Без ночной шкалы ночные чипы (127 из 420) давали F1 ≈ 0.
3. **Контекстный тест.** Кандидат — пиксель, у которого I4 выше фона в окне 71×71 на `k·σ` **и** ΔT больше порога.
   Фон считается по пикселям, не являющимися кандидатами, — как в операционном продукте VIIRS 375 м
   (Schroeder et al., 2014).
4. **Отсев техногенных источников.** Застройка и промплощадки (WorldCover 50): остаются только очаги крупнее 4 px
   и заметно сильнее типичного факела; одиночные слабые пиксели на пашне и открытой почве убираются.
5. **Классификатор очагов (`fires/blobfilter.py`) — второй режим, включаемый по валидации.** Кандидаты (мягкие
   пороги + результат правил) собираются в блобы 8-связностью; для каждого блоба считаются 23 признака (площадь,
   заполнение bbox, статистики I4/ΔT/I1/I3, доля блика, состав типов покрова, отношение периметра к площади, доля
   слабых тёплых пикселей вокруг) и решение принимает `HistGradientBoostingClassifier`. По одному пикселю газовый
   факел неотличим от пожара (I4 насыщен, ΔT даже выше), а по форме, площади и окружению — отличается.

   `train.py` обучает оба варианта и записывает в `weights.json` тот, который лучше на валидации
   (`af_mode: rules|blobs`). На реальном обучающем наборе победили правила: F1 0.9225 против 0.8980 у
   классификатора — размеченные очаги почти всегда настоящие, и модель начинает отсекать верные пиксели.

### 2.2. BS: гарь и степень поражения

1. `NBR = (B8A − B12)/(B8A + B12)`, `dNBR = NBR_pre − NBR_post`, `rdNBR = dNBR/√|NBR_pre|`.
2. Маскировка по SCL (облака, тени, снег, вода) и слою валидности.
3. Пороги dNBR **по типам покрова** (границы «горело / слабо / средне / сильно»): лес и кустарник —
   0.20 / 0.30 / 0.60, степь и пойма — 0.13 / 0.21 / 0.38, пашня и открытая почта — 0.12 / 0.19 / 0.37;
   застройка и снег не картируются. Значения измерены на реальных чипах: медианы dNBR классов 1/2/3 равны
   0.115 / 0.270 / 0.490 для пашни, 0.123 / 0.313 / 0.484 для степи и 0.173 / 0.390 / 0.726 для леса, а границы
   поставлены между распределениями. Единая шкала USGS для всех покровов стоит −0.076 Score (mIoU 0.386 → 0.146).
4. **Sentinel-1**: пиксели под облаком/тенью могут восстанавливаться по падению VH — эквивалентный
   `dNBR = −ΔVH / чувствительность` (лес ≈ 3 дБ на единицу dNBR, остальные покровы ≈ 1.5), порог срабатывания
   1 дБ. На реальном наборе выиграл вариант **без** восстановления (класс по ΔVH грубее оптического и добавляет
   ложные контуры), но подтверждение сильного падения VH осталось включённым. Режим выбирается на двух фолдах.
5. Постобработка: заполнение внутренних «дыр», удаление контуров меньше 6 px.

### 2.3. Ответ и его валидация

`inference.py` пишет CSV строго по шаблону: `chip_id,class_id,rle`; RLE — пары «начало длина» с 1, по возрастанию,
серии не пересекаются и **не соприкасаются** (соседние серии склеиваются), пустая строка допустима.
`--validate` проверяет: совпадение набора пар с `sample_submission.csv`, синтаксис RLE, выход за границы чипа и
пересечение масок разных классов внутри чипа.

## 4. Сервис

```bash
python -m service.catalog --data-dir /path/to/train --out service/catalog.json
CATALOG_PATH=service/catalog.json uvicorn service.app:app --host 0.0.0.0 --port 8000
```

| Метод | Назначение |
|---|---|
| `GET /` | веб-карта: контуры гари по степеням + термоточки, справка; без CDN и тайлов |
| `GET /api/health` | состояние каталога |
| `GET /api/thermopoints?bbox=…&date_from=…&date_to=…` | термоточки за период (GeoJSON) |
| `GET /api/burn-contours?severity=2,3` | контуры гари с атрибутами id, severity, area_ha, chip_id, date |
| `GET /api/report?format=json|csv` | площадь гари в га, распределение по трём степеням, число контуров |
| `POST /api/query` | территория (полигон или bbox) + даты → точки, контуры и справка одним вызовом |
| `GET /api/export/contours.geojson` / `.shp` | выгрузка контуров (GeoJSON; Shapefile — zip с .shp/.shx/.dbf/.prj) |
| `GET /api/catalog/reload` | перечитать каталог без перезапуска |

Каталог в репозитории собран по реальному обучающему набору в координатах WGS84: 9 478 термоточек и 1 126 контуров
гари на 94 084 га (32 718 / 37 269 / 24 097 га по степеням 1 / 2 / 3). Геопривязка берётся из `meta.csv`
(колонки `epsg`, `x_min`, `y_min`), при необходимости — из `chips_geo.csv`
(`chip_id,origin_lon,origin_lat,gsd,date,kind`); модуль `fires/geo.py` переводит UTM 37N/38N в градусы без pyproj
и GDAL. Если привязки нет (как в тестовой части кейса), каталог собирается в **демонстрационном** режиме — это
видно в `GET /api/report` (`catalog_mode`) и в шапке веб-карты. Ответ `submission.csv` от режима каталога не зависит.

## 6. Воспроизводимость и ограничения

* Все источники случайности зафиксированы (`SEED = 20260918`), обучение воспроизводится командой `train.py`.
* Инференс детерминирован: повторный прогон даёт побайтово одинаковый `submission.csv`.
* Разделение train/val — по `fire_event_id`, как у организаторов: чипы одного пожара не попадают в разные части.
* Метрика считается тем же способом, что и у организаторов: микро-агрегация по пулу пикселей, пустой класс = 1.
* Открытые библиотеки: numpy, scipy, scikit-learn, tifffile, FastAPI, uvicorn, pydantic, pyshp, matplotlib, pytest.
  Закрытых моделей и внешних API нет; FIRMS/MCD64A1 не используются.
* Ограничения: тестовой части набора нет, поэтому итоговый ответ для организаторов не построен (одна команда на
  месте); под облаками точность ограничена физикой (оптики там нет); 72 % ложных контуров BS приходится на пашню
  и открытую почву, где фенологический dNBR неотличим от слабого горения — главный резерв роста метрики.
