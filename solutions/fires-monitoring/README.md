# КосмоФАЙР-2 — решение кейса «Двухэтапный мониторинг природных пожаров по данным ДЗЗ»

КосмоХакатон · Красноярск · 18–20 сентября 2026.

Решение состоит из трёх сдаваемых частей, ровно как требует постановка:

| Часть | Что это | Где смотреть |
|---|---|---|
| **AF-модуль** | детекция активного горения по чипу VIIRS 375 м (I1–I5 + вспомогательные слои), бинарная маска | `fires/af.py`, `fires/blobfilter.py` |
| **BS-модуль** | картирование гари и степени поражения 0–3 по паре Sentinel-2 до/после и Sentinel-1 | `fires/bs.py` |
| **`submission.csv`** | RLE-маски по шаблону `sample_submission.csv` | `inference.py`, `fires/submission.py` |
| **Сервис** | информационно-аналитический сервис: REST API, GeoJSON/Shapefile, справка по площадям | `service/` |

Плюс сопутствующие артефакты: подбор параметров (`train.py`), метрика соревнования с абляциями (`evaluate.py`),
отчёт (`docs/report.md`), презентация (`docs/presentation.pdf|html`), тесты (`tests/`, 74 теста).

**Нужен только финальный ответ для организаторов?** Минимальный путь — четыре команды; полный порядок
действий с таймингами и проверками лежит в [`RUNBOOK.md`](RUNBOOK.md):

```bash
pip install -r requirements.txt
bash tools/prepare_test.sh ~/Downloads/fire-test-renamed.tar ~/firesdata/test   # распаковка теста
python -m fires.chips --data-dir ~/firesdata/test                               # диагностика раскладки
python inference.py --data-dir ~/firesdata/test --output submission.csv --validate
```

`--data-dir` — это каталог, внутри которого лежат `af/`, `bs/`, `meta.csv` и `sample_submission.csv`
(в архиве теста он вложен как `test/`, скрипт снимает лишний уровень сам).

## 2. Что именно делает решение

### 2.1. AF: детекция активного горения

1. **Скрининг.** Исключаются вода (WorldCover 80), невалидные пиксели и пиксели без термального наблюдения
   (NaN в I4/I5). Солнечный блик не выбрасывается (внутри блика может быть настоящий очаг), а переводится в
   «подозрительный» режим: нужен ΔT выше порога не менее чем на 9 K либо I4 ≥ 335 K.
2. **Раздельные дневные и ночные шкалы.** Днём фон I4 прогревается до 310–315 K, ночью — до 283 K, поэтому пороги
   зависят от зенитного угла Солнца (95°): насыщение 367/340 K, «очень яркий» очаг 360/310 K, минимум кандидата
   330/295 K, ΔT = I4 − I5 25/10 K. Без ночной шкалы ночные чипы (127 из 420) давали F1 ≈ 0.
3. **Контекстный тест.** Кандидат — пиксель, у которого I4 выше фона в окне 71×71 на `k·σ` **и** ΔT больше порога.
   Фон считается по пикселям, не являющимися кандидатами, — как в операционном продукте VIIRS 375 м
   (Schroeder et al., 2014).
4. **Отсев техногенных источников.** Застройка и промплощадки (WorldCover 50): остаются только очаги крупнее 4 px
   и заметно сильнее типичного факела; одиночные слабые пиксели на пашне и открытой почве убираются.
5. **Классификатор очагов (`fires/blobfilter.py`) — второй режим, включаемый по валидации.** Кандидаты (мягкие
   пороги + результат правил) собираются в блобы 8-связностью; для каждого блоба считаются 23 признака (площадь,
   заполнение bbox, статистики I4/ΔT/I1/I3, доля блика, состав типов покрова, отношение периметра к площади, доля
   слабых тёплых пикселей вокруг) и решение принимает `HistGradientBoostingClassifier`. По одному пикселю газовый
   факел неотличим от пожара (I4 насыщен, ΔT даже выше), а по форме, площади и окружению — отличается.

   `train.py` обучает оба варианта и записывает в `weights.json` тот, который лучше на валидации
   (`af_mode: rules|blobs`). На реальном обучающем наборе победили правила: F1 0.9225 против 0.8980 у
   классификатора — размеченные очаги почти всегда настоящие, и модель начинает отсекать верные пиксели.

### 2.2. BS: гарь и степень поражения

1. `NBR = (B8A − B12)/(B8A + B12)`, `dNBR = NBR_pre − NBR_post`, `rdNBR = dNBR/√|NBR_pre|`.
2. Маскировка по SCL (облака, тени, снег, вода) и слою валидности.
3. **Сглаживание dNBR** медианой 3×3: соседние пиксели горят вместе, а одиночные выбросы (границы полей,
   тени, сдвиг сцен) дают россыпь ложных контуров. Размер окна выбран по двум фолдам — 0.2932 против 0.2850
   у варианта без сглаживания.
4. Пороги dNBR **по типам покрова** (границы «горело / слабо / средне / сильно»): лес и кустарник —
   0.25 / 0.35 / 0.65, степь и пойма — 0.12 / 0.21 / 0.38, пашня и открытая почта — 0.10 / 0.19 / 0.37;
   застройка и снег не картируются. Значения измерены на реальных чипах: медианы dNBR классов 1/2/3 равны
   0.115 / 0.270 / 0.490 для пашни, 0.123 / 0.313 / 0.484 для степи и 0.173 / 0.390 / 0.726 для леса, а границы
   поставлены между распределениями. Единая шкала USGS для всех покровов стоит −0.125 Score.
5. **Sentinel-1**: пиксели под облаком/тенью могут восстанавливаться по падению VH — эквивалентный
   `dNBR = −ΔVH / чувствительность` (лес ≈ 3 дБ на единицу dNBR, остальные покровы ≈ 1.5), порог срабатывания
   1 дБ. На реальном наборе выиграл вариант **без** восстановления (класс по ΔVH грубее оптического и добавляет
   ложные контуры), но подтверждение сильного падения VH осталось включённым. Режим выбирается на двух фолдах.
6. **Степень поражения: пороги или обученная модель.** Постановка строит эталон порогами dNBR, поэтому
   пороговый режим — база, а не заглушка. Но порог — это одно число на группу покрова, а решение о степени
   зависит и от запаса биомассы (NDVI до пожара), и от текстуры пятна, и от радиолокационного отклика.
   `fires/severity.py` считает 23 признака пикселя и решает задачу градиентным бустингом
   (`HistGradientBoostingClassifier` на CPU или `xgboost` с `device="cuda"` на GPU; веса классов ∝ 1/√n,
   набор признаков переключается флагом `--features base|ext`, где `ext` добавляет каналы видимого диапазона,
   влажность B11/B12, рельеф, текстуру dNBR и сезон). Модель считается только внутри области
   интереса (dNBR > 0.05 — около 30 % пикселей чипа), режим выбирается на отложенной части по событиям пожара:
   **IoU_burn 0.5391 против 0.4871 и mIoU_sev 0.5146 против 0.4793 у порогов** при одинаковой морфологии и
   сглаживании, то есть +0.029 Score по BS-части. Дальше модель доводится циклом
   `tools/train_loop.py`: 15 конфигураций (ёмкость, признаки, веса сложных покрытий, бэггинг по сидам,
   ансамбль, смещения классов, пространственная постобработка вероятностей, морфология) с отчётом
   «улучшилось / нет» по каждому шагу и итогом «до и после» на отложенной части и на всём обучающем
   наборе; найденные сглаживание и фильтр большинства записываются в файл модели и работают при
   инференсе. Если файла модели нет или он собран другой версией scikit-learn, решение молча
   возвращается к порогам.
7. Постобработка: удаление контуров меньше 48 px; внутренние «дыры» контура модель заполнять не даёт
   (она отличает их от гари), в пороговом режиме они заполняются.

### 2.3. Ответ и его валидация

`inference.py` пишет CSV строго по шаблону: `chip_id,class_id,rle`; RLE — пары «начало длина» с 1, по возрастанию,
серии не пересекаются и **не соприкасаются** (соседние серии склеиваются), пустая строка допустима.
`--validate` проверяет: совпадение набора пар с `sample_submission.csv`, синтаксис RLE, выход за границы чипа и
пересечение масок разных классов внутри чипа.

строился; весь конвейер при этом отработан на реальных 644 чипах.

Числа выше — на всей обучающей части. Для BS это включает 168 чипов, на которых обучалась модель степени
поражения, поэтому честная оценка обобщения — **56 отложенных чипов** (`fire_event_id` не пересекаются):
IoU_burn **0.5391** и mIoU_sev **0.5146** против **0.4871 / 0.4793** у порогов при той же морфологии.

**Время.** На тестовом по составу наборе (макет из 180 AF + 89 BS чипов) `inference.py` идёт **34.6 с на двух
ядрах** (2 процесса; четыре процесса поверх двух ядер не помогают — 39 с) и по числу чипов и ядер укладывается
в **≈10–12 с на 6-ядерной машине**. Лимит кейса — 30 с на прогон (за 8 баллов скорости; 5 минут — 6 баллов,
12 минут — 4, 30 минут — 2). На 6-ядерном CPU с 12 потоками стоит поднять число процессов: `--jobs 12` (по
умолчанию — ядра, не больше двенадцати), а число потоков внутри воркера решение нормирует само (ядра / число
процессов), чтобы процессы не дрались за одни и те же ядра. В отчёте инференса печатаются `seconds` и
`seconds_per_chip` — по ним видно, что дало изменение. Если машина слабее, режим BS переключается
одной строкой `"bs_mode": "thresholds"` в `weights.json`: тогда тот же набор считается ≈7 с (цена — 0.029 Score
на отложенной части, см. п. 3.3 отчёта).

## 4. Сервис

```bash
python -m service.catalog --data-dir /path/to/train --out service/catalog.json
CATALOG_PATH=service/catalog.json uvicorn service.app:app --host 0.0.0.0 --port 8000
```

| Метод | Назначение |
|---|---|
| `GET /` | веб-карта: контуры гари по степеням + термоточки, справка; без CDN и тайлов |
| `GET /api/health` | состояние каталога |
| `GET /api/thermopoints?bbox=…&date_from=…&date_to=…` | термоточки за период (GeoJSON) |
| `GET /api/burn-contours?severity=2,3` | контуры гари с атрибутами id, severity, area_ha, chip_id, date |
| `GET /api/report?format=json|csv` | площадь гари в га, распределение по трём степеням, число контуров |
| `POST /api/query` | территория (полигон или bbox) + даты → точки, контуры и справка одним вызовом |
| `GET /api/export/contours.geojson` / `.shp` | выгрузка контуров (GeoJSON; Shapefile — zip с .shp/.shx/.dbf/.prj) |
| `GET /api/catalog/reload` | перечитать каталог без перезапуска |

Каталог в репозитории собран по реальному обучающему набору в координатах WGS84: 9 478 термоточек и 4 892 контура
гари на 256 520 га (92 675 / 107 248 / 56 597 га по степеням 1 / 2 / 3). Геопривязка берётся из `meta.csv`
(колонки `epsg`, `x_min`, `y_min`), при необходимости — из `chips_geo.csv`
(`chip_id,origin_lon,origin_lat,gsd,date,kind`); модуль `fires/geo.py` переводит UTM 37N/38N в градусы без pyproj
и GDAL. Если привязки нет (как в тестовой части кейса), каталог собирается в **демонстрационном** режиме — это
видно в `GET /api/report` (`catalog_mode`) и в шапке веб-карты. Ответ `submission.csv` от режима каталога не зависит.

## 5. Структура

```
fires-monitoring/
├── inference.py            # обязательный CLI постановки: --data-dir → --output
├── train.py                # подбор порогов и обучение (очаги + модель степени поражения) → weights/
├── evaluate.py             # метрика соревнования и абляции
├── fires/
│   ├── chips.py            # автоопределение раскладки датасета, каналов и масок (+ CLI-диагностика)
│   ├── af.py               # AF: скрининг, абсолютные и контекстный тесты, отсев техногенных источников
│   ├── blobfilter.py       # ML-фильтр очагов: признаки блобов + HistGradientBoosting
│   ├── bs.py               # BS: dNBR, пороги по покровам, Sentinel-1, постобработка
│   ├── severity.py         # обучаемая модель степени поражения (23/40 признаков, CPU или CUDA)
│   ├── morphology.py       # дилатация/эрозия/закрытие/заполнение дыр/маркировка (scipy или fallback)
│   ├── metrics.py          # метрика кейса: F1_af, IoU_burn, mIoU_sev, Score по пулу пикселей
│   ├── submission.py       # RLE-кодек и валидация ответа по шаблону
│   ├── vectorize.py        # контуры из масок (обход границы + Дуглас—Пекер) и площади
│   ├── weights.py          # загрузка/сохранение weights.json
│   └── synthetic.py        # генератор синтетического набора (CLI), для отладки и тестов
├── service/
│   ├── catalog.py          # каталог сцен: термоточки, контуры, справка
│   └── app.py              # FastAPI: REST, GeoJSON, Shapefile, веб-карта
├── tools/
```

## 6. Воспроизводимость и ограничения

* Все источники случайности зафиксированы (`SEED = 20260918`), обучение воспроизводится командой `train.py`.
* Инференс детерминирован: повторный прогон даёт побайтово одинаковый `submission.csv`.
* Разделение train/val — по `fire_event_id`, как у организаторов: чипы одного пожара не попадают в разные части.
* Метрика считается тем же способом, что и у организаторов: микро-агрегация по пулу пикселей, пустой класс = 1.
* Открытые библиотеки: numpy, scipy, scikit-learn, tifffile, FastAPI, uvicorn, pydantic, pyshp, matplotlib, pytest.
  Закрытых моделей и внешних API нет; FIRMS/MCD64A1 не используются.
* GPU не обязателен: инференс параллелится по ядрам CPU и укладывается в лимит 30 с, GPU ускоряет только
  обучение модели степени поражения (`xgboost` с CUDA). Модель, обученная на GPU, читается и считается на CPU;
  переключатель — `--device auto|cpu|cuda` в `train.py`, `tools/train_loop.py`, `inference.py`, `evaluate.py`.
* Ограничения: тестовой части набора нет, поэтому итоговый ответ для организаторов не построен (одна команда на
  месте); под облаками точность ограничена физикой (оптики там нет); на отложенных чипах 66 % ложных пикселей BS
  приходится на пашню и открытую почву (ещё 32 % — на степь), где фенологический dNBR неотличим от слабого горения
  — главный резерв роста метрики вместе с расширением обучающей выборки.
