# CosmoH starter kit — КосмоХакатон 18–20.09.2026

Заготовки под два кейса (Красноярск + Санкт-Петербург), чтобы на старте не терять часы на
каркас, а сразу решать содержательную часть.

```
starter/
  fires-krasnoyarsk/   # К1: «Оперативный мониторинг лесных пожаров» (ДЗЗ, ML, веб-сервис/API)
  orbital-risk-spb/    # К3: «Орбитальный риск» (космическая погода, радиация, система алертов)
```

## Быстрый старт

```bash
cd starter/fires-krasnoyarsk
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python -m cosmofire.cli demo          # генерирует данные, считает метрики, кладёт отчёт в data/
uvicorn cosmofire.service:app --port 8000
# открыть http://localhost:8000
```

Аналогично для `starter/orbital-risk-spb` (`python -m cosmorisk.cli demo`, затем uvicorn).

## Важно про правила (прочитать до старта!)

Положение (пп. 8.8, 9.5, 9.6, 11.1):

* Организатор умеет проверять **историю репозитория** и заимствования.
* Использовать открытые библиотеки, данные и **свои** ранее созданные компоненты можно —
  но только с раскрытием источников и с явным указанием того, что сделано **в период хакатона**.
* Нельзя выдавать за результат команды полностью готовое чужое решение и скрывать существенный
  объём заранее созданного решения.

Поэтому правильная схема такая:

1. Этот starter kit живёт в **отдельном репозитории** как «техническая заготовка» (или как папка
   с явным дисклеймером в README).
2. Для сдачи создаётся **новый репозиторий**, в котором история коммитов показывает работу команды
   в окне хакатона; в README — раздел «Disclosure»: какие открытые библиотеки и заготовки
   использованы, что именно сделано командой в 18–20.09.
3. Содержательная часть (модель, данные, фичи, UI, презентация) делается/дописывается в окне
   хакатона — это и есть предмет оценки.

Готовые к использованию модули этого кита ускоряют старт, но не заменяют конкурсную работу.
